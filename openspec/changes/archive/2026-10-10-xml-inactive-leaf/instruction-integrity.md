## Owner decision batch

1. **Leaf-list values with a per-value `inactive`.** Evidence: the device captures show an inactive leaf with one value (`<vlan-id inactive="inactive">751</vlan-id>`, set `deactivate … unit 751 vlan-id`), not one inactive value among several. XML input today nests such a value as `{"@": …, "members": ["64496:2"]}`; set input `deactivate policy-options community C1 members 64496:2` marks the whole leaf-list and drops the value. Effect: the IR's `@members` marker cannot say which value is inactive; widening it would deactivate active values silently. Device artefact needed (name a path, never the whole configuration), on a lab candidate with `rollback` afterwards: `set policy-options community C1 members [ 64496:1 64496:2 ]`, then `deactivate policy-options community C1 members 64496:2` (does the CLI accept it?), then `show policy-options community C1`, `… | display set`, `… | display xml`, `… | display json`. Safe default until it arrives: every value inactive → sibling `@members`; only some inactive → reported as a statement that cannot be placed.
2. **Assurance preference** (`economy`, `balanced` or `maximum-assurance`). Effect: `balanced` adds an independent Test/Challenge pass and a fresh Reviewer for this yellow-zone change; `economy` adds neither. Change B is cross-domain (schema, conversion, kernel), so it gets both roles whatever you choose. Safe default: `balanced`, as for the last two changes.
3. **Merging A before B is implemented.** Evidence: B's characterization tests include the XML inactive leaf, and `batches.md` says merge a predecessor before implementation starts on a change that needs its code. The prompt says "do not push", which does not cover a local merge. Effect: either you fast-forward A into `master` locally after its review, or B branches from A's branch and you merge both in order. Safe default: B's phases 0–4 run on a branch stacked on A; B's implementation starts after you merge A.
