Three defects in junoscfg's own code are fixed. An absolute `--path` (or `convert_config(path=...)`) ending at a leaf, leaf-list or flag now keeps that statement's tags, as the selection of its parent writes them, in every output format: `--path system.host-name` of a deactivated host name writes `deactivate system host-name` (structured `inactive:`, JSON and YAML `"@host-name"`), where it wrote the statement active. Selected relative (`--relative`), such a statement's tags now follow the rule for a tag on the selected statement itself, as a selected container's already did: set writes bare `deactivate`, `protect`, `activate` or `delete` commands, structured writes the "N tag(s) of the selected statement itself dropped" note. A `yaml` document with a mapping key that is not a string (`64496: x`, an unquoted `on: x`) is refused with its kind and path, as `yaml-new` refuses it ("a YAML int key at configuration has no JSON spelling", CLI exit 2), where conversion and audit crashed with `AttributeError`; quote such a key. `yaml` validation, which crashed with `TypeError` on such a key or judged valid a document holding one under a leaf, a cycle, or a value nested more than 64 levels deep (`host-name: {1: x}`, `host-name` holding 70 nested lists), now reports what the `yaml` reader refuses as invalid (`-v` exit 1). JSON and XML input with a value nested more than 64 levels deep, anywhere in a JSON document, outside `configuration` too, is refused with its path ("a JSON value at ... is nested deeper than 64 levels", CLI exit 2). junoscfg crashed with `RecursionError` on such input (JSON past about 448 levels, XML whose element repeats at each level past 163) and converted it below that, which is refused now too; JSON validation (`-v -i json`) reports it invalid where it said "Validation: OK". No Junos configuration nests deeper than about 28 levels counting groups, or holds a cycle or a key that is not a string.
