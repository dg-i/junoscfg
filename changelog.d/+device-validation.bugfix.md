Validation no longer rejects what a device printed. The schema model now declares the statements a device writes inside `<undocumented>` and Juniper's XSD leaves out: login user `shell`, grpc `clear-text port` and `skip-authentication`, ddos-protection `autoconf aggregate bandwidth|burst`, inet6 labeled-unicast `per-prefix-label` and dhcp-local-server `stale-timer`/`no-stale-timer-refresh`. An element a schema fix renames to its CLI keyword keeps the name the device writes in XML and JSON (`end-range`, `ieee-802.3ad`, IS-IS `hello-padding-type`, ...): set and curly use the keyword, JSON and yaml-new use the element name, and every reader gives the same configuration one IR. JSON and yaml-new output of such a statement read from set, curly, XML or yaml input now spells it as the device does (`"ieee-802.3ad"`, `"end-range"`), and JSON validation rejects the keyword there; legacy `yaml` output of JSON input holds the keyword, as for every other reader. `protocols isis-instance ... application-specific attribute-group` and the routing-instance, logical-system and tenant copies of the device's singleton lists are lists. Set validation reads `protect`, `activate`, `delete` and `deactivate` lines as statement paths, which may stop before a leaf's value, and quotes an invalid line whole. Field validation no longer checks `$junos-` dynamic-profile variables as values. A JSON, yaml-new or YAML validation message names the failing path and keys and no longer reprints the configuration. XML input whose `<interfaces>` holds only `<interface-range>` is read as the container it is.
